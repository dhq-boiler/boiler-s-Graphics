## 1. 概要

### 1.1 目的
ユーザーが自分で描いた図形群を **「パーツ (Part)」** として登録し、そのパーツに **公開パラメータ (Exposed Properties)** を定義して、配置のたびに数値・色・本数などで形を変えられるようにする。

### 1.2 この機構が満たすべき体験
1. キャンバス上の図形を 1 つ以上選択し、コンテキストメニューやショートカットから **「パーツ化」** を実行できる。
2. パーツ化された結果は **パーツ定義 (Part Definition)** としてプロジェクト内に登録される。
3. パーツ定義に対し、内部図形のプロパティ (位置、サイズ、色、線種、繰り返し数等) を **公開パラメータ** として宣言できる。
4. パーツをキャンバスの好きな位置に **インスタンス** として配置できる。配置数に上限は設けない。
5. 各インスタンスの公開パラメータは独立に編集でき、形が即座に変わる。
6. パーツ定義そのものを編集すると、既存インスタンスへ反映される (反映の同期方針は §5 参照)。

### 1.3 非スコープ (Phase 1-a では扱わない)
- パーツライブラリ UI (一覧パネル、検索、サムネイル、ドラッグ&ドロップ配置 等)
- アニメーション (Phase 5 以降)
- スクリプト/式によるパラメータの算出 (Phase 7 以降)
- パーツの Variant (Figma の Component Variants 相当)

### 1.4 Phase 1-a のスコープに含むもの (改めて整理)
- パーツ定義の作成・編集 (別ウィンドウ方式、§5.4)
- パーツインスタンスの配置・パラメータ編集
- パーツインスタンスの切り離し (Detach、§5.5)
- パーツ定義のクローン加工 (Clone & Customize、§5.6)
- **パーツ定義の単独ファイル保存/読込** (`*.bgpart`、§10 Q-5 案 B 採用)
- パーツ定義の入れ子 (§5.3)
- 公開パラメータの 8 型 + 配列型サポート (§10 Q-2, Q-2b)

## 2. 用語定義

| 用語 | 意味 | UI 表記 (案) |
|---|---|---|
| **パーツ (Part)** | 1 つ以上の図形をまとめた再利用可能な単位 | 「パーツ」 |
| **パーツ定義 (Part Definition)** | パーツの中身 (図形構成 + 公開パラメータの宣言) の "型" | 「パーツ定義」 |
| **パーツインスタンス (Part Instance)** | パーツ定義をキャンバスに配置した実体 | 「パーツインスタンス」 |
| **公開パラメータ (Exposed Property)** | パーツ定義のうちインスタンス側から書き換え可能なパラメータ | 「公開プロパティ」 |
| **バインディング (Binding)** | 内部図形の特定プロパティと公開パラメータを結び付けるマッピング | 「バインディング」 |

UI 文言は日本語優先 ([[development-priorities]] §13)。**§10 Q-1 で「パーツ」/ `Part` を採用と決定済み** (代替案だった「コンポーネント」「部品」「シンボル」は不採用)。

## 3. データモデル

### 3.1 全体図

```
PartDefinition  ─┬─ Name : string
                      ├─ Id   : Guid
                      ├─ Items : ObservableCollection<DesignerItemViewModelBase>   // 中身の図形
                      └─ ExposedProperties : ObservableCollection<ExposedProperty>

ExposedProperty       ─┬─ Name        : string         // ユーザー表示名 ("半径", "リング数" 等)
                       ├─ Type        : ExposedPropertyType  // Double / Int / Boolean / Point / Color / Brush / String / Enum
                       ├─ IsArray     : bool           // true なら可変長配列として扱う (Q-2b 案 A)
                       ├─ DefaultValue: object
                       ├─ Bindings    : List<Binding>  // どの図形のどのプロパティに反映するか
                       └─ Constraints : Constraints?   // Min/Max/Step 等 (任意)

Binding               ─┬─ TargetItemId  : Guid                 // PartDefinition.Items 内の図形 Id
                       ├─ TargetProperty: string               // プロパティ名 ("Width" / "Stroke" 等)
                       └─ Transform     : IValueTransform?     // 任意。スケール・オフセット・式 (Phase 7 以降で式対応)

PartInstance     ─┬─ Id           : Guid
                       ├─ DefinitionId : Guid     // 参照する PartDefinition.Id
                       ├─ Left/Top/Rotation 等 (DesignerItemViewModelBase 由来)
                       └─ ParameterValues : Dictionary<ExposedPropertyId, object>
                                       // 公開パラメータごとのインスタンス側の値
```

### 3.2 クラス配置案
- `PartDefinition` / `ExposedProperty` / `Binding` → `boilersGraphics\Models\Parts\` (新規ディレクトリ)
- `PartDefinitionViewModel` → `boilersGraphics\ViewModels\Parts\`
- `PartInstanceViewModel : DesignerItemViewModelBase` → 同上 (既存 DesignerItem の派生として扱う)

### 3.3 既存モデルとの関係
- `PartInstance` は `DesignerItemViewModelBase` を継承し、既存の選択・移動・整列・グループ化の挙動を流用する。
- 中身の図形 (`PartDefinition.Items`) は既存の `DesignerItemViewModelBase` 派生 (NRectangleViewModel 等) を流用する。`PartDefinition` 専用の図形クラスは作らない (実装コストとテスト範囲を抑えるため)。

## 4. UI フロー

### 4.1 パーツ化フロー
1. キャンバスで図形を選択 (複数可)。
2. 右クリック → 「パーツ化…」を選択 (またはショートカット)。
3. ダイアログが開き、パーツ名を入力。
4. OK 押下で:
   - 選択された図形群が `PartDefinition` として登録される。
   - 元の場所に **そのパーツの最初のインスタンス** が自動配置される (見た目は変わらない)。
   - 元図形は `PartDefinition.Items` に移管される。
5. プロパティパネルが「パーツインスタンス」モードに切り替わり、公開パラメータが (初期は空のリストで) 表示される。

### 4.2 公開パラメータの宣言フロー
1. パーツ定義を編集状態に入る (パーツインスタンスをダブルクリック → 編集モードへ。詳細は §5.4)。
2. 編集モード中に内部図形を選択すると、プロパティパネルの **各プロパティ行の右端に「公開状態アイコン」が常時表示** される。
   - **非公開**: グレーアウトしたアイコン (例: 中抜きのピン / 鍵 / 矢印)
   - **公開済み**: 強調表示のアイコン (例: 塗りつぶしのピン)
   - ホバーでツールチップ: 「このプロパティを公開する」 / 「公開を解除する」
3. アイコンをクリックすると **公開状態がトグル** される:
   - 非公開 → 公開: 小さなインライン入力 (or 軽量ダイアログ) で公開パラメータ名 (例: `幅`)、デフォルト値、必要なら制約を指定。
   - 公開 → 非公開: 確認なしで Binding 解除 (誤操作対策として直近 1 回 Undo 可能)。
4. 公開済みのプロパティはプロパティパネルで視覚的に区別される (背景色を変える / ラベル横に「公開: <パラメータ名>」と表示など)。
5. 公開パラメータが `PartDefinition.ExposedProperties` に追加され、選択中の図形のそのプロパティが Binding として登録される。
6. 1 つの公開パラメータに **複数の Binding** を持たせることも可能。
   - 操作例: 既に公開済みパラメータ「半径」がある状態で、別の図形の `Width` プロパティのアイコンをクリック → 「新規公開」と「既存のパラメータに紐づける (ドロップダウンから選択)」を選べる UI を出す。
   - こうすることで「半径」が、5 個のリング図形それぞれの `Width`/`Height` に反映されるような構成が組める。

> **設計上の利点**: 状態がアイコンとして常時可視化されるため、ユーザーは「この図形のどのプロパティが公開されているか」を一目で把握できる。Figma の Component Properties や、IDE のブレークポイント表現に近い感覚。

### 4.3 インスタンス配置フロー
- パーツライブラリ UI は Phase 1-a では作らない (非スコープ)。
- 代替として:
  - 既存インスタンスを **コピー&ペースト** で複製
  - 既存インスタンスを **複製コマンド (Duplicate)** で増やす
  - これらの操作は既存 boilersGraphics の機能で動くようにする

### 4.4 パラメータ編集フロー
- パーツインスタンスを選択 → プロパティパネルに公開パラメータ一覧が表示 → 値を編集 → 中身の図形がリアクティブに再構成される。

## 5. 編集動作仕様

### 5.1 パーツ定義とインスタンスの同期方針 (Q-4 確定済み)
- パーツ定義の **構造変更** (図形の追加・削除、公開パラメータの追加・削除) → 既存全インスタンスに即時反映 (Figma 型)。
- 公開パラメータの **値** はインスタンスごとに独立 (反映されない)。
- インスタンス側で内部図形を直接編集することは **できない** (オーバーライド禁止)。設計哲学: 非公開パラメータを変えるということは、もうそのパーツではない (詳細は §10 Q-4)。
- ユーザーが非公開部分を変えたい場合の逃げ道として、以下を提供する:
  1. **パーツ定義を編集する** (§5.4 の別ウィンドウ編集モードに入り、全インスタンスに反映する形で変える)
  2. **パーツインスタンスを切り離す (Detach / Explode)** — §5.5 参照。生図形に展開し、以後パーツとの同期は失われる
  3. **派生パーツを新規定義する** — 既存パーツ定義を複製して別パーツとして登録する (Phase 1-a でサポート、UI 詳細は実装時)

### 5.2 リアクティブ反映
- 既存の R3 1.3.0 を活用。`PartInstance.ParameterValues` の変更が、Binding を介して中身図形のプロパティに反映される。
- 反映方向は **公開パラメータ → 内部図形** の単方向 (双方向にすると循環参照のリスク)。

### 5.3 パーツの入れ子 (Part-in-Part)
- Phase 1-a では **入れ子を許可する**。ただし循環参照は禁止 (登録時にチェック)。
- 再帰深さは無制限とするが、実装上スタックオーバーフローを防ぐためのガードを入れる (例: 深さ 32 で警告)。

### 5.4 パーツ定義の編集モード (Q-3 案 B: 別ウィンドウ方式)
- パーツインスタンスをダブルクリック (または右クリック → 「パーツ定義を編集」) すると、**そのパーツ定義専用の独立したエディタウィンドウ** が開く。
- 別ウィンドウ内には、編集対象パーツの中身 (`PartDefinition.Items`) のみが表示され、独立したキャンバス・ツールバー・プロパティパネルを持つ。
- 元のプロジェクトウィンドウは閉じずに残り、編集対象のインスタンスは「編集中」マーカーで示される。
- 別ウィンドウで編集を保存すると、開いている全プロジェクトの全インスタンスに反映される (§5.1)。
- **派生メリット (Q-3 採用の決め手)**:
  - パーツ定義はウィンドウ単位で独立しているため、**個別ファイル (例: `*.bgpart`) としてセーブ/ロードする UI** が自然に組み込める。
  - 他のプロジェクトでも同じパーツファイル (`*.bgpart`) を開いて再利用できる (§10 Q-5 案 B 確定済み)。
  - 別ウィンドウなのでマルチモニタ環境で「左にプロジェクト、右にパーツ編集」のような使い方ができる。
- **実装上の留意点**:
  - 別ウィンドウは独立した `Window` (WPF) として実装する。
  - ウィンドウ間でパーツ定義の参照は同一の `PartDefinition` インスタンスを共有する (リアクティブ反映のため)。
  - ウィンドウを閉じる際、未保存変更があれば確認ダイアログを出す。

### 5.5 パーツインスタンスの切り離し (Detach) — Q-4 派生機能
- パーツインスタンスを右クリック → 「パーツから切り離す (Detach)」を選ぶと、そのインスタンスが **生図形群に展開** され、パーツ定義との関連が失われる。
- 切り離し後、ユーザーは展開された各図形を自由に編集できる (もはやパーツインスタンスではないため)。
- パーツ定義そのものや他のインスタンスは影響を受けない。
- Undo で切り離し前の状態に戻せる。

### 5.6 パーツ定義のクローン加工 (Clone & Customize) 🌟
パーツ定義そのものを **複製して、別のパーツとして加工できる** 機能を Phase 1-a の必須機能として組み込む。

- **操作フロー**:
  1. 既存のパーツ定義を選択 (パーツ一覧パネル、または既存インスタンスを右クリック)
  2. 「**複製して新パーツとして開く (Clone & Customize)**」を選ぶ
  3. 新パーツ名を入力するダイアログが開く
  4. 確定すると、**別ウィンドウで新パーツ定義の編集画面が開く** (§5.4 と同じウィンドウ機構を使う)
  5. ユーザーは新パーツを自由に編集できる (図形の追加・削除、公開パラメータの再定義、Binding の組み替え 等)
- **複製されるもの**:
  - 内部図形 (`PartDefinition.Items`) のディープコピー
  - 公開パラメータ定義 (`ExposedProperties`) と Binding の全コピー
  - 制約 (Min/Max/Step 等) もそのまま継承
- **複製されないもの**:
  - 既存インスタンス (新パーツのインスタンスは 0 個から始まる)
  - 元パーツとのリンク (クローン後は完全に独立した別パーツ。一方を編集してもう一方に影響なし)
- **意義**:
  - サンプルパーツ (Phase 1-e) を起点に、ユーザーが自分専用のバリアントを派生できる
  - 既存パーツの 80% を流用して 20% だけ違うパーツを作りたいケース (例: 「3 重リング」→「5 重リング」、「直線目盛り」→「曲線目盛り」) を低コストで実現できる
  - FUI 制作のワークフロー上、ベースのアイディアを少しずつ変えて試行錯誤するのに必須
- **§5.4 (別ウィンドウ編集モード) との関係**: クローン操作後の編集ウィンドウは、§5.4 の編集モードと同一の UI/機構を使う (新規パーツ定義として開かれるだけ)

## 6. シリアライズ仕様

### 6.1 既存形式
boilersGraphics は `ObjectSerializer.cs` / `ObjectDeserializer.cs` で XML シリアライズしている (詳細は実装時に確認)。

### 6.2 パーツ定義のプロジェクト内保存
- プロジェクトファイル内に `<PartDefinitions>` セクションを新規追加。
- 各パーツ定義は Guid (Id) を持ち、インスタンスからはこの Guid で参照する。

### 6.3 インスタンスの保存
- 既存の DesignerItem 配列の中に `<PartInstance DefinitionId="...">` として並ぶ。
- インスタンスは公開パラメータの値だけを持つ (`<ParameterValues>` ノード)。

### 6.4 後方互換
- 既存プロジェクトファイルは `<PartDefinitions>` セクションを持たない。読み込み時に **未存在ならスキップ** (空リストとして扱う)。
- 新形式で保存しても、`<PartDefinitions>` が空なら旧バージョンでも開ける可能性がある (要検証)。

### 6.5 パーツ定義の単独ファイル保存 (`*.bgpart`) — Q-5 案 B 採用
- 1 つの `PartDefinition` を 1 ファイルとして XML シリアライズする。
- ファイル構造 (案):
  ```xml
  <BoilersGraphicsPart Version="1" Id="GUID">
    <PartDefinition Name="..." ...>
      <Items>...</Items>
      <ExposedProperties>...</ExposedProperties>
    </PartDefinition>
  </BoilersGraphicsPart>
  ```
- 拡張子: **`.bgpart`** (Q-5b で再確認)
- 保存/読込 UI:
  - パーツ編集ウィンドウ (§5.4) に「名前を付けて保存 (`.bgpart`)」コマンドを追加
  - プロジェクトの「インポート → パーツ」コマンドで `.bgpart` を読み込み、現プロジェクトの `<PartDefinitions>` に追加
- 同一 ID のパーツがプロジェクト埋め込みと外部ファイルで衝突した場合の解決ルールは **§10 Q-5c** で別途決める

## 8. テスト戦略

`boilersGraphics.Test` (NUnit 4.3.2 + Moq 4.20.72) に追加するテスト案:

1. **モデル単体**: `PartDefinition` / `ExposedProperty` / `Binding` のプロパティ動作・等値性
2. **バインディング反映**: 公開パラメータ変更 → Binding 経由で内部図形プロパティが変わるリアクティブ動作
3. **シリアライズ**:
   - パーツ定義 + インスタンスがある状態で保存 → 読み込みで完全復元
   - 旧形式 (パーツ定義なし) のプロジェクトを読み込んでもクラッシュしない
4. **入れ子**:
   - 入れ子可能
   - 循環参照は登録時に拒否される
5. **構造変更の反映**: パーツ定義に公開パラメータを追加 → 既存インスタンスに新パラメータが現れる
6. **既存テスト**: [[project_test_baseline]] (209 個) はすべて緑のまま

カバレッジは Phase 1-a の完了基準とせず、テストが追加され緑であることをもって最低限とする。

## 9. 既存基盤との接続点 (実装時の参照ポイント)

実装着手 (Phase 1-b) 時に詳細を確認すべき既存コードの位置 (Phase 0 棚卸し済み):

- `DesignerItemViewModelBase` (`boilersGraphics\ViewModels\DesignerItemViewModelBase.cs`) — `PartInstanceViewModel` の親

### Q-1. 用語: 「部品」「コンポーネント」「シンボル」「パーツ」どれを使う? ✅ **確定**

### Q-2. 公開パラメータの型サポート範囲 ✅ **確定**
- **採用する型 (Phase 1-a)**:
  - `Double` — 連続値 (半径、角度、長さ、不透明度 等)
  - `Int` — 離散値 (本数、頂点数、リング数 等)
  - `Boolean` — トグル (表示/非表示、点線ON/OFF 等)
  - `Point` — 2D 座標 (中心点、始点・終点 等)
  - `Color` — 単色 (`System.Windows.Media.Color`)
  - `Brush` — 塗りつぶし全般 (`SolidColorBrush` / `LinearGradientBrush` / `RadialGradientBrush`)
  - `String` — テキストパーツ用 (ラベル、ダミーデータ文字列 等)
  - `Enum` — 既定の選択肢 (線種、矢印スタイル 等)
- **不採用**: `GeometryData`
  - 理由: ジオメトリ全体を不透明な値として持つのはパラメトリックの逆。形状の構成要素 (頂点座標 `Point`、半径 `Double`、頂点数 `Int` 等) に **分解して個別に公開** することで自由な形状を表現する。
  - 例: 多角形の形を変えたいなら、`GeometryData` を公開するのではなく、`Point[]` や「頂点数 + 半径」のような基本型の組み合わせで公開する (配列型は §10 Q-2b で **案 A: Phase 1-a で配列型サポート確定**)。
- **後送り**: `Expression` (式) は Phase 7 (スクリプタビリティ) で扱う
- **配列型サポート**: §10 Q-2b で **案 A 確定**。Phase 1-a で `Point[]`, `Double[]` 等の配列型もサポートする。

### Q-2b. 配列型 (`Point[]`, `Double[]` 等) を Phase 1-a で扱うか? ✅ **確定**
Q-2 で `GeometryData` を分解する判断に伴い派生したオープン問題。

- **採用: 案 A (Phase 1-a で配列型サポート)**
- 確定日: 2026-05-12 (作者判断)
- **採用理由**: 不規則形状 (任意位置の頂点を持つ多角形、自由な座標群) を表現するために必要不可欠。`GeometryData` を分解する方針 (Q-2) を本気で貫くなら、配列型サポートは避けられない。
- **データモデル反映**: `ExposedProperty` に `IsArray : bool` フィールドを追加。`Type` と直交させることで、`Double` 単体 / `Double[]` の両方を 1 つの型システムで表現する。
- **Phase 1-a に追加で必要な実装**:
  - 配列要素の追加・削除・並び替え UI (プロパティパネル内のリスト UI)
  - 配列要素を Binding ターゲットへ展開する仕組み (例: `Point[]` の各要素が、可変個の図形のプロパティに 1:N マッピングされる)
  - シリアライズ拡張 (`<Values><Value>...</Value>...</Values>` 等)
- **影響範囲**: スコープ拡大は認めつつ、UI の優先度は「スカラー型 → 配列型」の順で実装する

### Q-3. パーツ定義編集モードの UI 表現 ✅ **確定**
- **採用: 案 B (別ウィンドウでパーツ定義を開く / After Effects のプリコンポーズ風)**
- 確定日: 2026-05-12 (作者判断)
- **採用理由**: パーツ定義が独立したウィンドウになることで、**パーツファイルとして単独でセーブ/ロードできる UI が自然に組み込める** (Q-5 と連動)。マルチモニタでの作業性も向上。
- **検討した代替**: 案 A (フォーカスモード) — 実装はシンプルだが、パーツの独立ファイル化に繋げにくい
- **Q-5 への影響**: パーツ定義の保存スコープ (現状「プロジェクトファイル内のみ」) を **「プロジェクト内 + 単独ファイル (`*.bgpart` 等) の両対応」** へ拡張する方向で再検討する (Q-5 に反映)

### Q-4. インスタンス側で内部図形の "オーバーライド" を許すか ✅ **確定**
- **採用: 案 A (オーバーライドを許さない / 公開パラメータ経由のみ)**
- 確定日: 2026-05-13 (作者判断)
- **採用理由 (作者言)**: 「公開パラメータでのみいじれるようにすべき。その他の非公開パラメーターをいじったらそのパーツではなくなる」
- **設計哲学 — パーツのアイデンティティ論**:
  - **公開パラメータ**: パーツの同一性を保ったまま変えられる差分。これをいじったインスタンスは依然として "同じパーツ" である。
  - **非公開パラメータ**: ここを変えたいということは、それはもう "そのパーツではない" ということ。
  - したがって、もし非公開部分を変えたいなら、それはパーツのインスタンスではなく、(a) パーツ定義を編集して全インスタンスに反映するか、(b) パーツから "切り離して" ただの図形群にするか、(c) 別の派生パーツを新規定義するか、のいずれかを選ぶ。
- **派生する Phase 1-a の必要機能**:
  - 「パーツインスタンスを切り離す (パーツから生図形へ展開する)」操作 (= Detach / Explode 相当)
  - これにより、ユーザーが非公開部分を編集したくなった時の逃げ道を提供する
- **不採用**: 案 B (Visibility のみオーバーライド可) / 案 C (完全オーバーライド可)
- **§5.1 との整合**: §5.1「インスタンス側で内部図形を直接編集することはできない」と完全に一致

### Q-5. パーツ定義の保存スコープ ✅ **確定**

- 確定日: 2026-05-13 (作者判断)
- **採用理由**:
  - Q-3 で別ウィンドウ方式 (案 B) を採用したことにより、パーツ単独ファイルとしての保存/読込フローが自然に組み込める
  - クローン加工 (§5.6) の元パーツとして、自プロジェクト内のパーツも外部ファイルのパーツも両方使える
  - 将来のパーツライブラリ機能 (Phase 1-a 後) への布石
- **ファイル形式**:
  - 拡張子: **`.bgpart`** (boilersGraphics Part の略。要再確認 → Q-5b 参照)
  - 内容: 単一の `PartDefinition` (内部図形 + 公開パラメータ + Binding) を XML シリアライズ
- **保存先**:

  - 単独ファイル `*.bgpart` として保存する (新規、§6.5 として追加)
  - 両者は同じパーツ定義 ID (`Guid`) を持ち得るが、Phase 1-a ではプロジェクトロード時に両方読み込まれた場合は「プロジェクト埋め込み優先」とする (詳細は §10 Q-5c で別途)
- **派生する新オープン問題**:

  - **Q-5c**: 同一 ID のパーツがプロジェクト埋め込みと外部ファイルの両方に存在する場合の解決規則

### Q-5b. パーツ単独ファイルの拡張子は何にするか? ✅ **確定**

### Q-5c. パーツ ID 衝突の解決規則 ✅ **確定**
プロジェクトファイルに埋め込まれているパーツ定義と、外部 `*.bgpart` ファイルからインポートされたパーツ定義が同一 `Guid` を持つ場合の扱い。

- **採用: 案 A (プロジェクト埋め込みを優先)**
- 確定日: 2026-05-13 (作者判断)
- **採用理由**: 上書きは事故のリスクが高い。インポート時にユーザーが気付かないまま既存パーツが書き換わるのを防ぐため、安全側に倒す。
- **具体的な解決ルール**:
  1. インポート時にプロジェクト内に同一 `Guid` のパーツが既に存在するかチェック
  2. 存在する場合:
     - 内容が **完全一致** なら何もしない (黙ってインポートを完了)
     - 内容が **異なる** なら、外部側のパーツに **新しい `Guid` を払い出し**、表示名を `"{元の名前} (インポート)"` に変えて別パーツとして追加する
  3. 存在しない場合: そのままインポート
- **ユーザーへの通知**: ステータスバー or 軽量トーストで「N 件のパーツをインポートしました (うち M 件は同名衝突のためリネーム)」程度を出す。モーダルダイアログは出さない (操作の流れを止めない)。
- **不採用**:
  - 案 B (外部側で上書き) — 既存作業の破壊リスク
  - 案 C (ダイアログで選ばせる) — 操作の流れを止める、判断疲れを生む
- **影響**: パーツインポート UI、シリアライズ仕様、内容比較ロジック (XML 構造の正規化比較が必要)

### Q-6. 「公開する」操作の入口 ✅ **確定**

- 確定日: 2026-05-13 (作者判断、提案も作者)
- **採用理由**: 状態が常時可視化されるため発見性が高く、Figma の Component Properties や VSCode のブレークポイント表現に近い直感的な UX。
- **検討した代替** (いずれも不採用):
  - 案 A: 右クリック → 「公開する」 (操作が隠れていて発見しづらい)
  - 案 B: サイドパネルからプロパティをピック (画面の往復が必要)
  - 案 C: A + B 両方 (UI 重複)
- **詳細仕様は §4.2 を参照**
- **実装上の留意点**:

  - アイコンは Material Design Icons あたりから採用候補を Phase 1-b で決定 (ピン / 鍵 / 矢印など)
  - 公開状態のスタイル区別 (色の濃淡、ボーダー等) はテーマと整合させる

### Q-7. リアクティブ反映の実装方式 ✅ **確定**
- **採用: 案 A (R3 ベース)**
- 確定日: 2026-05-13 (作者判断)
- **採用理由**: 既存コードベースが R3 1.3.0 主流。意図ファイル §2.1 「既存の MVVM (Prism) / Rx (R3) パターンを徹底する。新たに別パターンを混ぜ込まない」と一致。
- **具体的な実装方針**:
  - `ExposedProperty` の各値は `ReactiveProperty<T>` または等価なものとして保持
  - `PartInstance.ParameterValues` も `ReactiveProperty<T>` を辞書状に保持
  - `Binding` は、`ExposedProperty.Value` を Subscribe して内部図形のターゲットプロパティに書き込む subscriber 関数として実装
  - 配列型 (Q-2b) は `ObservableCollection<ReactiveProperty<T>>` または `ReactiveCollection<T>` 系で表現
- **不採用**: 案 B (旧来 INPC + WPF Binding) — 既存コードベースとパターンが混ざるため
- **影響**: テスト容易性が向上 (R3 のスケジューラを差し替えて同期的テストが書ける)、既存テスト [[project_test_baseline]] のパターンを踏襲できる

### Q-8. パーツインスタンスの "リサイズ" の意味 ✅ **確定**
- **採用: 案 B (リサイズ不可。位置と回転のみ。サイズは公開パラメータ経由)**
- 確定日: 2026-05-13 (作者判断)
- **採用理由**: Q-4 「非公開パラメータをいじったらもうそのパーツではない」と一貫。見た目のサイズも本来公開パラメータで決めるべき表現であり、リサイズ枠で曖昧にスケールされるのは設計哲学に反する。
- **不採用**: 案 A (スケール変換) — Illustrator のシンボル風だが、パラメトリック性が崩れる
- **実装上の留意点**:
  - パーツインスタンスは `DesignerItemViewModelBase` を継承するため、標準ではリサイズハンドルが効いてしまう
  - リサイズ系の Adorner / Behavior を **パーツインスタンス時のみ無効化** する仕組みが必要 (例: `IsResizable` プロパティを `DesignerItemViewModelBase` 側に追加し、`PartInstance` で `false` に固定する、または専用 Adorner Style を当てる)
  - 選択枠は描画する (位置・回転ハンドルは有効、サイズハンドルのみ非表示 or 無効)
- **派生する UX 配慮**:
  - パーツインスタンスを選択した時、プロパティパネルで「サイズを変えるには公開パラメータ (例: `半径`) を使ってください」のヒントを表示するとよい (Phase 1-b 実装で検討)

### Q-9. サンプルパーツの同梱方針 ✅ **確定**
- **採用: 案 C (同梱せず、チュートリアルでユーザーに作らせる)**
- 確定日: 2026-05-13 (作者判断)
- **採用理由**: 意図ファイル §2.6 「完成済みテンプレートは配布しない、ユーザー自身が組み上げる」と一貫。サンプルファイルを配布すると、それを起点にしたコピペ文化が生まれて創造性をスポイルする。
- **不採用**:
  - 案 A (ビルド時組み込み + 自動投入) — テンプレート配布と等価
  - 案 B (別ファイル `.bgpart` 群として配布) — 形を変えたテンプレート配布
- **代わりに提供するもの (Phase 1-e の役割再定義)**:
  - **docs/fui/tutorials/** 配下に **作り方ドキュメント** を整備する (Markdown)
  - 例: `tutorial-concentric-rings.md` (同心円リングをゼロから作る手順)
  - 例: `tutorial-tick-marks.md` (目盛りジェネレータをゼロから作る手順)
  - チュートリアルには **完成形のスクリーンショット** と **再現手順** を載せる。`.bgpart` ファイルは添付しない
- **影響**: Phase 1-e のスコープが「実装」から「ドキュメント整備」に変わる。サンプル *の作り方* を文書化することで、本ツールの設計哲学 (§2.6) を作者自身が実践した記録となる
